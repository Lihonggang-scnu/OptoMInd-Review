# WO-01 — Preserve owner results, fresh material, cache compatibility, and bounded batch recovery

## Objective

Repair the owner/recovery and chapter-detail persistence path so a later failure cannot erase a compatible earlier success, corrected materials cannot be replaced by stale packets, compatible work reuses its cache, and bounded chapter batches retain useful successful output without declaring an empty merge complete.

## Scope and files

- `optomind_research/runtime/upgrade3/progressive_review_plan.py`
  - `_post_case_review`
  - `_classify_owner_response`
  - `_chapter_details`
  - `_chapter_details_adaptive_record`
  - `_chapter_details_cache_signature`
  - adjacent owner cache/recovery and chapter-batch helpers actually used by these functions.
- Existing targeted tests/fixtures under `tests/upgrade3/` and advisor fixtures may be extended only as bounded offline checks; do not add domain-specific production prompt text.

## Required behavior

1. Keep the last compatible successful owner result separate from the most recent failed attempt. A later chapter failure and a subsequent resume must not overwrite a usable earlier result.
2. Treat current A/B, directed-reading, supplement, and local-fragment inputs as authoritative for the current attempt. A stale packet cannot replace a corrected supplement merely because its cache entry exists.
3. Normalize accepted `shared_outline` list/object shapes before owner classification while retaining chapter ownership validation.
4. Compare `assigned source_materials` and `candidate_navigation` through separate cache projections. Identical effective inputs reuse; a substantive material/task change invalidates only the affected work.
5. Reuse an early-stage cache only when the research question/scope, material view, stage prompt, and relevant parameters are compatible. If an old cache lacks sufficient input provenance, do not assume compatibility and do not invalidate the entire work directory.
6. When an oversized chapter is split, persist each successful batch. An empty `units` merge, missing substantive chapter, or failed batch cannot overwrite a valid prior chapter or be marked complete.

## Concrete acceptance examples

- Two chapter updates run in order; the second fails; resume keeps the first updated result and does not call the first update again.
- Only supplement content changes; the corrected content appears in the final owner message and the old supplement is not reintroduced.
- The same `candidate_navigation` produces no duplicate generation; changing a task or material produces a bounded new attempt.
- A batch merge with empty `units` leaves the prior valid chapter intact and records the failed seam for recovery.
- A normal, unsplit chapter with no new material retains its existing output and ordinary call path.

Tests must read persisted records/messages, not only the return value of a helper. A fixture may replace the model/network boundary but must call the real recovery and cache functions.
