# WO-03 — Initialize retrieval, reuse complete needs, and isolate supplement retries

## Gate

WAITING_APPROVAL. Begin only after explicit root approval following WO-01 and the directed-reading contract review.

## Scope

- `optomind_research/runtime/upgrade3/planning_retrieval_loop.py`: `run_retrieval_loop` and query initialization/state handling.
- `optomind_research/runtime/upgrade3/planning_supplement.py`: supplement attempt allocation, result persistence, and feedback classification.
- `optomind_research/runtime/upgrade3/progressive_review_plan.py`: `make_retrieval_loop_runner`, supplement adapter, cross-stage need assembly, and owner feedback handoff.

## Actions

1. On the first retrieval round, inherit an effective query from the current need or retrieval plan; if none exists, call the existing query refiner once and persist its result before retrieval. Never require a failed retrieval to create the first query.
2. If query initialization fails, report “query not formed” with the need and reason. Do not report “no literature found,” inject topic-specific keywords, or loop without a bound.
3. Key cross-stage reuse by research content and acceptance requirements, then bind the current chapter owner separately. A compatible answered need is reused once; an owner change alone does not repeat supplement work.
4. If the question or required outputs change, preserve reusable material but mark the new portion outstanding and supplement only the missing part. A partial answer cannot become `answered` by shape alone.
5. Give each supplement retry a new attempt directory and route downstream consumers to that actual returned path. Keep the failed attempt for diagnosis.
6. Retain useful failed/partial/unmet feedback even when optional `gap_id` or fulfillment fields are absent. Keep existing budget and quota accounting; do not reset historical reservations or introduce a new retrieval policy.

## Quality examples

- Empty first query reaches the existing initializer and then the retrieval boundary once.
- The same need across level-2 and chapter stages causes one external retrieval/supplement and two owner bindings.
- Changed `required_outputs` produces a new attempt while retaining the old material.
- A second supplement uses a new directory and its material appears in the owner message and pool.
- A failed feedback row without optional metadata remains visible to the next coordinator.

## Dependencies and record

Use F06, F07, F10, and F15 evidence in `references/`; cite retrieval fixture IDs or `LOCAL_ONLY`. Record query lifecycle, attempt directories, external-boundary call count, reuse key, partial/unmet state, and budget ledger observations.

## Limits

Bounded offline checks only. No paid retrieval, full planning/body run, unbounded retry, credential use, or full test suite. WO-04 and WO-05 remain closed until explicit approval after this package.
