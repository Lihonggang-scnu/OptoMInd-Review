## 修了什么，怎样检查

### F1 编排缓存与正式写作入口

`scripts/upgrade3/chapter_arrangement.py::saved_payload_from` 保存 `source_briefs`、`portion`、`issues`；旧导出格式的 `_payload_from_saved` 也保留 issues。没有把新生成段落 ID 当成原任务 ID 来猜关联。

`review_unit_writer.py::load_arrangement` 在共享文件入口消费现有 validation：明确失败、未完成或矛盾结果不进入材料读取、客户端构造和写作输出。独立 CLI 自动获益，无需第二套 CLI 判断。无 validation 的真正旧格式兼容；有正向 validation 的结果仍需没有相反信号。普通 advisory issue 并不自动阻断一个已验证编排。

实际普通、合并、拆分任务都经过 fresh CLI→缓存落盘→恢复→validator→独立 writer CLI。修后 fresh/cache 的写作消息一致，原任务、拆分范围、负责人条件保留；无效编排拒绝写作并保留既有正文文件的字节。旧缓存已经丢掉的关联无法靠本次保存修复凭空恢复：继续标记失败，不自动重付费、不伪造关系。

见 [F1 记录与前后产物](f1/README.md)。

### F2 恢复真正到达内层，并保留有效内容

`ProgressiveReviewPlanner._tool_cycle` 的 adaptive 分支每次进入既有 collector，外层仍保存当前实际参数和结果；兼容性与已满足复用由内层持久化缓存负责。不是清除所有缓存。legacy 非 adaptive 注入路径没有改写，不能把此次证据泛化到该路径。

真实内层复现进一步发现：同需求已被 journal 标记停止后，显式 `retry_empty_result` 即使到达 collector 仍会恢复旧停止行。为此给 `run_retrieval_loop` 增加默认空的 `retry_need_ids`，仅显式重开匹配的未回答末次尝试。已回答结果不重读，旧日志及有用 partial 不删除；一个显式重试不自动启动一串新的研究轮次，原供应商基础设施重试上限也没有增加。

同一需求恢复成功后，活动章节材料采用累计的新结果，避免旧未回答行与新答案并列。不同需求身份不会被合并删除；历史尝试仍在落盘日志中。实际恢复/新要求测试还检查：保留旧有用答案时，其来源、条件与实质限制也同时保留，不只拼接孤立文本。

### F3 早期规划消息不漏掉本地答案

`_compact_tool_feedback` 复用 `_tool_material_for_prompt`，增加来源绑定的本地答案、条件、限制以及轻量需求状态。验证真实 `level1_outline` 消息和 `RUN_STATE.stage_inputs`，不是只检查工具返回 JSON；没有把索引片段、材料池或完整尝试日志再次塞入请求。

当前需求完成时，已解决缺口不能又以 `still_missing` 或工具自动镜像的 gap-limit 复活。只识别既有生产 writer-material schema 中精确镜像的旧任务缺口，保留真实来源限制，不做语义猜测或科学判定。
