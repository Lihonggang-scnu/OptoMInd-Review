## 2. 决策摘要

可以修，重点是修通路，不重做正文规划架构。

问题有三类：

1. **已有信息没被正确交付。** 负责人成功结果在恢复时被覆盖、补充材料回退、工具来源缺引用身份、独立返回的表格被解析器丢掉。
2. **本来应该取得的信息没有取得。** 首轮缺查询直接停止、重试撞旧目录、同论文新任务被旧任务缓存或数据库规则挡住。
3. **规划意图和后到材料没有持续参与后续决策。** 全文主张被范围说明替代、晚到论文缺正式路由入口、早期缓存和位置式 ID 对修改不够稳健。

这些问题具有明确修复价值。但不能由此断言修完必然恢复到旧稿的 176 篇、相同章节数或相同文字质量。旧稿还经历过编辑反馈、负责人更新和两个单元的选用试写；它不是与新稿所有条件相同的自动运行对照。旧版生产代码的完整身份仍有未确认项，应保留未知，不能由目录日期反推提交。

## 3. 实施期间必须保持的行为

1. 保留当前恢复后的 BODY 顺序：**全局协调与负责人修订 → 案例正式附加 → 编排 → 单元写作**。不重新引入案例之后整章再审批、再压缩的流程。
2. 轻量首尾仍由正文完成后的独立模块负责。本方案不恢复并行 manuscript-parts 分支，也不修改其生产策略。
3. 修复对所有主题生效。真实电解质、微生物组材料只作测试样本，不能把它们的答案、特征数字或术语写入通用提示词。
4. **内容是否可用与每篇是否有独立 A/B 是两回事。** 原始研究的具体内容已由综述或工具材料提供时，该原始研究只需可解析的引用身份；不强制下载、重读，不降低这种材料的权重。单有题名/DOI 而任何输入都没有研究内容，则不能凭空展开。
5. **任务完成按内容判断。** 两个比较任务可合理合并为一张表；一项任务也可由正文与表格共同完成。表格数、论文数、模型自报 covered IDs 都不能单独证明完成。
6. 保留部分有用答案，同时区分“可用部分”与“整个缺口已解决”。不因不完美删掉有价值材料，也不因 JSON 非空就宣布满足需求。
7. 不新建审稿平台、第二套 planner 或无界检索循环。复用现有 reader、store、retrieval loop、协调者和 writer。
8. 沿用账本及现有可配置名额，不重置历史费用，不重新释放未知占额。本方案不授权任何付费调用。完整真实测试继续等待云端审核后授权。

### 01：修负责人恢复、材料更新、缓存和分批失败保存

**主要文件**：`optomind_research/runtime/upgrade3/progressive_review_plan.py`。

**切入点**：`_post_case_review`、`_classify_owner_response`、负责人 cache/recovery 读写、`_chapter_details`、`_chapter_details_adaptive_record`，以及早期阶段恢复逻辑。

**执行**：

1. 分开“最近一次尝试”与“当前仍可使用的最近成功结果”。后章失败不能覆盖已经成功且输入相容的前章；再次恢复从成功结果接着执行。
2. 当前 A/B、精读、补充、本地片段是本轮权威输入。恢复不能用旧 packet 覆盖已修正的新材料。比较实际被消费的内容，时间戳和路径变化本身不触发重做。
3. shared_outline 支持实际出现的列表与对象形状，先统一内部结构；不降低章节归属检查。
4. 分离 assigned source_materials 与 candidate_navigation 的缓存比较投影。相同输入恢复零新增调用；材料或任务实质变化只重做受影响部分。
5. 早期阶段复用至少检查研究问题/范围、材料视图、该阶段提示词及参数是否相容。复用既有缓存机制；旧缓存无充分输入记录时不得默认认定相容，也不要把整个工作目录全部失效。
6. 超限章节保留每批成功结果。合并器返回空 units、缺实质章节或某批失败时不能记成完整成功；保留可用批次并从失败接缝恢复。正常未超限章节流程不变。

**验收样例**：两章依次更新，第二章失败，再次 resume 后第一章更新仍在且不重调；只改补充材料时新内容留在最终消息；相同 candidate_navigation 不触发重复生成；空合并结果不覆盖已有有效章节。必须读取落盘结果，不仅检查函数返回值。

**停点一**：01 完成即交验，确认没有用“拒绝一切缓存”代替正确恢复。

### 02：打通同论文新任务及无效精读的真实重试

**主要文件**：`directed_reading.py`（含 `DirectedReadingStore`）、`progressive_review_plan.py` 的真实精读 adapter，以及实际使用的 practical 内容判定函数。

**执行**：

1. 论文身份与阅读任务分开。同论文的新问题或新 required_outputs 能生成独立任务/输出位置；同一已满足任务直接复用。名额仍按现有“独立论文”口径，不因一篇多任务重复扣篇数。
2. SQLite add_task 与 reader 输出目录的规则同步修改，不能只改上层 adapter。问题字符串应转换为实际合同字段，避免 purpose 为空导致不可执行。
3. 复用须有本次问题需要的实际内容。非空 question 数组不等于有回答；有用但不全的内容保留为 partial。
4. 对明确无实际答案的结果，提供一次显式 retry 路径，同时绕过该次失败结果缓存和 RAW_RESPONSE；旧尝试保留。没有显式重试不得建立自动付费循环。

**验收**：通过真实 store、真实 reader 和实际缓存；仅模型/网络边界替身。依次测试同任务复用、新问题、新输出要求、空答案重试、有用 partial 保留。断言替身是否真正被调用，不能让上层 fake 直接返回成功遮住下层错误。

### 03：修补充检索初始化、跨阶段复用与重试

**主要文件**：`planning_retrieval_loop.py`、`planning_supplement.py`、`progressive_review_plan.py` 的 `make_retrieval_loop_runner` / supplement adapter。

**执行**：

1. 首轮先继承当前需求或对应检索规划中已有的有效查询。仍为空时调用现有 query refiner 初始化一次，保存结果再检索。不得要求先有失败检索才能生成第一条查询。
2. 初始化仍失败，报告“查询未形成”，保留需求和原因；不能说“未检索到文献”。不无限重试，不硬塞本题关键词。
3. 需求的研究内容/验收要求与当前章节 owner 分开。跨阶段完全相容且已回答的需求复用材料与完成状态，再绑定本轮 owner；owner 改变本身不触发再次研究。
4. 问题或预期输出改变时，不误复用为已完成；可复用原有有用材料，再补新增部分。只回答一半的需求不得整体标 answered。
5. supplement 失败后创建新的 attempt 目录；各下游读取本次实际返回路径。原目录保留，不清空历史文件逃避错误。
6. 保留 failed/partial/unmet 的有用反馈，即便缺少可选 gap_id 或 fulfillment_judgment；只约束当前计划可写范围，不推导领域不存在相关研究。
7. 保留已有全局预算与名额。历史讨论过的 6/40/80/120 等检索数值不直接恢复成新硬限制，本包不重设计采样策略。

**验收**：首轮空 query 经现有初始化真正到达检索边界；相同需求跨 level2/chapters 仅一次外部调用；改 required_outputs 后能补研究；第二次 supplement 使用新目录且新材料进入判断和池；失败反馈进入负责人实际消息。

**停点二**：02–03 完成交验，只做局部离线测试，不用重新跑大题验证重试是否有效。

### 04：统一当前身份、可用内容与晚到论文的入口

2. 对池外实际论文沿用既有身份加入流程。无法定位时保留可用材料和未解决身份，不借用另一篇 P 号。
3. 负责人来源准入检查实际送达的全部合法材料渠道：source_materials、candidate_materials、精读、补充、章节工具材料及综述转述。嵌套 paragraph_briefs 等实际承载引用的字段一并检查。
4. 有真实综述转述内容及引用身份的原始研究正常准入；只有身份、没有任何研究内容的候选留待选，不自动编造成正式研究案例。
5. 已读候选被采纳后，将它的真实材料或转述材料关系带入正式 packet；不能只放行 handle 然后让下游又失去内容。处理同 handle 不同身份冲突，不能拼成旧身份加新 A/B。
6. 章节工具材料所引用的、可解析的独有来源加入 source_catalog 和 writer 允许引用范围；原始研究可以只有身份条目，内容仍来自工具材料。不将所有未知句柄直接放进白名单。
7. 对晚到论文增加正式的增量路由入口。先沿用取得材料时已有的相关章节与用途；无法确定时使用现有路由器处理增量，不重跑全池。不强制每篇新论文进入案例，但必须具备被选择的机会。

**验收**：旧索引 P 号与本轮 P 号指向不同论文仍绑定正确；工具独有来源可引用；身份加综述转述合法通过；纯身份且无任何转述不能伪造内容；candidate_materials 中的已读候选被采纳后内容到达 writer；晚到论文进入增量路由且不扩大无关章节输入。

### 05：保住全文组织意图与增量更新关系

**主要文件**：`progressive_review_plan.py`、`chapter_arrangement.py`、`review_unit_writer.py` 及其 CLI 的全局信息装配。

**执行**：

1. 将 shared_scope 与 review_argument 作为不同信息保留。一级主张是暂拟认识，现有全局协调者依据最终材料校准后，最终计划、packet、编排和写作读取这个校准结果；不拿 scope.statement 顶替。
